## 1. 배경

### 지금 규칙의 한계

정원은 **자습실 단위**다(규칙 #2, 명세의 "자습실별 신청 인원(취소 제외)은 최대 인원을 넘을 수 없다"). 신청·목록이 모두 `status = 'APPLIED'`인 신청 수만 세고 **방문 시각을 보지 않는다.** 그래서 실제 자습실 운영과 어긋나는 경우가 생긴다.

- **끝난 방문도 자리를 차지한다.** 18~20시 학생의 방문이 끝나도 신청은 `APPLIED`로 남아 정원 1자리를 계속 쓴다. 자리가 나는 경우는 시작 전 취소, 학생 삭제, 정원 증가뿐이다.
- **시간이 겹치지 않아도 정원을 나눠 쓴다.** 정원 1자리 자습실에서 10~12시 학생이 신청해 두면, 저녁 19~21시는 비어 있는데도 마감으로 보인다.

### 레퍼런스

좌석 배치도로 자습실을 관리하는 화면(번호가 붙은 좌석, 재석·공석·특이사항)을 참고했다. 이 화면에는 두 가지 성격이 섞여 있다.

| 성격             | 내용                                                            | 이번 범위                                                                                       |
| ---------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 좌석 지정        | 자습실에 번호가 붙은 좌석이 정해져 있고 학생이 특정 좌석을 쓴다 | **포함**                                                                                        |
| 실시간 재석 관리 | 재석·외출·쪽잠·이탈·조퇴 등 "지금 실제로 있는지"                | **제외** — 입실·퇴실 체크(출결)가 있어야 나오는 정보. 지금 시스템은 "언제 오기로 했는지"만 안다 |

## 2. 방향 비교

|                   | A. 시간대별 정원              | **B. 좌석 직접 선택 (채택)**                         | C. 좌석 자동 배정                  |
| ----------------- | ----------------------------- | ---------------------------------------------------- | ---------------------------------- |
| 정원 규칙         | 구간 안 동시 인원 ≤ 최대 인원 | **같은 좌석의 시간 겹침 금지** (최대 인원 = 좌석 수) | B와 같음, 좌석은 서버가 배정       |
| 18~20시 → 20~22시 | 가능                          | 가능                                                 | 가능                               |
| 학생 경험         | 시간만 고름                   | 시간 + **좌석 선택**(배치도)                         | 시간만 고르고 좌석 번호를 안내받음 |
| 강사 경험         | 시간대별 인원                 | **시각별 좌석 배치도**                               | 시각별 좌석 배치도                 |
| 스키마            | 변경 없음                     | 좌석 테이블, 신청에 좌석                             | B와 같음                           |
| 규모              | 중간                          | **큼**                                               | 큼 (B보다 작음)                    |

B를 고른 이유: 실제 자습실·독서실처럼 "몇 번 좌석"을 학생이 정하고, 강사는 좌석 배치도로 현황을 본다. 시간대별 정원 문제(1절)도 함께 해결된다.

### B에서 새로 생기는 성질: 좌석 단편화

좌석 방식은 시간대별 정원(A)보다 **엄격하다.** 좌석 2개 중 1번 좌석이 18~20시, 2번 좌석이 20~22시로 예약돼 있으면, 19~21시는 매 순간 한 자리씩 비어 있어 A로는 신청할 수 있다. 하지만 **19~21시 내내 비어 있는 좌석이 하나도 없어서** B로는 신청할 수 없다. 실제 독서실처럼 "한 자리에 계속 앉는다"는 규칙이다. 학생 화면은 고른 시간 내내 비어 있는 좌석만 고를 수 있게 하고, 없으면 시간을 바꾸거나 다른 자습실을 고르도록 안내한다.

명세의 "최대 인원"은 **"좌석 수"로 해석**한다. 실제 자습실은 좌석 단위로 운영되고, 동시에 앉을 수 있는 최대 인원이 곧 좌석 수이기 때문이다. 이 해석은 README의 정한 규칙 #2에 근거와 함께 남긴다.

## 5. 바뀌는 곳

> 대기열 제거(결정 3)는 별도 이슈에서 먼저 끝낸다. 아래는 **대기열이 없는 상태**를 기준으로 한다.

### 5-1. DB (스키마·마이그레이션)

| 대상              | 변경                                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| `seats` (신규)    | `id`, `study_room_id`, `number`(좌석 번호, 자습실 안에서 유일), `created_at`. 격자 위치는 번호로 계산(한 줄 5석) |
| `visits`          | `seat_id` 추가 — 처음엔 NULL 허용으로 추가 → 기존 데이터 이전 → 유효 신청은 좌석 필수(서비스 로직)               |
| `visit_histories` | `prev_seat_id`, `seat_id` — "3번 → 5번 좌석" 변경도 이력으로                                                     |
| 인덱스            | `visits (seat_id, status, start_at)` — 좌석별 겹침 조회                                                          |

- **같은 좌석 겹침 금지는 DB 제약이 아니라 서비스 로직**으로 검사한다. 배제 제약(`EXCLUDE USING gist`)은 Prisma 스키마로 표현할 수 없어, PostgreSQL이 조건을 다른 형태로 저장하면 드리프트가 생긴다(#31·#36에서 확인).
- **좌석을 줄일 때 (구현에서 정함, #45 PR 1)**: 좌석 행은 **지우지 않는다.** `number > max_personnel`인 좌석은 쓰지 않는 좌석으로 본다. 지난 예약·취소·이력이 좌석을 계속 참조할 수 있고, 최대 인원을 다시 늘리면 같은 번호의 좌석을 그대로 다시 쓴다. `deleted_at`을 두면 다시 늘릴 때 같은 번호가 유니크 제약에 걸려 되살리는 처리가 따로 필요해서 이 방식을 골랐다. 줄일 때 막는 기준은 "없어질 좌석에 **아직 끝나지 않은** 유효 신청"이다(지난 예약·취소는 막지 않음).
- **기존 데이터 이전 마이그레이션** (가장 까다로운 부분)
  1. 기존 자습실마다 좌석 1~`max_personnel`번을 만든다. 30석 초과 범위는 새로 등록·수정할 때만 검사한다(기존 자습실은 그대로 이전).
  2. 기존 유효 신청을 방문 시작 순으로 보며, 시간이 겹치지 않는 가장 작은 번호 좌석에 배정한다. 지금은 유효 신청 수 ≤ 최대 인원이 보장되므로 모두 배정할 수 있다.
  3. 취소된 신청은 좌석 없이(NULL) 둔다 (결정 7). 재신청할 때 좌석을 고른다.

### 5-2. 공유 타입 (`packages/shared`)

- 신규 타입: `Seat { id, number }`, 좌석별 예약 현황(그 시간에 비어 있는지, 예약자)
- 좌석 필드 추가: `Visit`·`StudyRoomVisit`·`StudyRoomHistory`(이전·이후 좌석)
- 요청: `CreateVisitRequest`·`UpdateVisitRequest`에 `seatId`
- `StudyRoom`: `currentPersonnel`은 유효 예약 건수로 유지(결정 8). 시간과 무관한 "남은 자리" 숫자는 두지 않는다(결정 4)
- 상수: 최대 인원 상한 30, 한 줄 좌석 수 5
- 에러 코드: `SEAT_TAKEN`(그 시간에 이미 예약된 좌석), `SEAT_NOT_FOUND`, `SEATS_IN_USE`(예약이 있는 좌석은 줄일 수 없음). `CAPACITY_FULL`·`CAPACITY_BELOW_CURRENT`는 대체되므로 정리

## 6. 진행 계획

한 PR로 하면 리뷰도 되돌리기도 어렵다. 그래서 **대기열 제거를 먼저 별도 이슈로 끝내고**, 좌석 전환은 **구현 이슈 하나에 PR 여러 개**로 나눈다. 각 PR 안에서도 lint·타입을 통과하는 단계마다 작게 커밋한다.

| 순서 | 이슈·PR         | 내용                                                                                                                                                                        |
| ---- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | 대기열 제거     | 대기열 API·테이블·웹·테스트를 걷어내고 규칙 #14·대기열 문서를 "구현했다가 좌석 방식으로 바꾸며 뺀 기능"으로 정리 (별도 이슈)                                                |
| 1    | 좌석 모델과 API | 스키마, 기존 데이터 이전, 신청·수정 규칙, 좌석 현황 API, e2e. **좌석을 지정하지 않으면 서버가 빈 좌석을 자동 배정**해서, 3번이 들어오기 전까지 지금 화면이 깨지지 않게 한다 |
| 2    | 학생 화면       | 좌석 배치도 컴포넌트, 신청 다이얼로그 2단계, 좌석 번호·좌석 수 표시, 정원 마감 안내                                                                                         |
| 3    | 강사 화면       | 시각별 좌석 배치도, 좌석 수 설정, 목록의 "N석 · 예약 M건"                                                                                                                   |
| 4    | 문서·시드·캡처  | 규칙·README·솔루션 문서, 캡처 다시 촬영                                                                                                                                     |

1번의 자동 배정은 이후 "아무 좌석이나" 선택지로도 쓸 수 있다.

## 7. 범위 밖

- **대기열** (결정 3): 좌석 지정 대기가 다시 필요해지면 겹침이 모두 풀렸을 때 제안, 대기 중 시간에 걸리는 연장·신청 제한을 함께 설계한다
- **실시간 재석 관리** (레퍼런스의 재석·외출·쪽잠·이탈·조퇴): 입실·퇴실 체크와 출결 상태가 필요한 별도 도메인
- **좌석 배치 편집기** (통로·벽·출입문을 그리는 자유 배치)와 열 수 설정
- **좌석 속성** (창가, 콘센트 등)과 선호 좌석 추천

## 8. 위험

- **변경 범위가 넓다.** DB·API·웹·테스트·문서가 모두 바뀐다. 그래서 대기열을 먼저 걷어내고, 단계별 PR로 나누고, 1번 PR의 자동 배정으로 중간 상태에서도 앱이 동작하게 한다.
- **기존 데이터 이전**: 운영 데이터가 있다는 가정에서 마이그레이션이 실패하지 않도록, 배정 로직을 테스트 DB에서 먼저 검증한다.
- **명세와의 거리**: "최대 인원 = 좌석 수"는 해석이다. 평가자가 읽을 수 있게 근거를 README에 남긴다.
- **좌석 단편화**: 시간대별 정원보다 받을 수 있는 신청이 줄어든다. 학생 화면에서 "그 시간 내내 비어 있는 좌석이 없어요 → 시간을 바꾸거나 다른 자습실"로 분명히 안내해야 한다.
- **대기열 제거**: 이미 병합한 기능(#36)을 빼는 일이다. 왜 만들었고 왜 뺐는지 문서에 남겨 판단 과정이 보이게 한다.
