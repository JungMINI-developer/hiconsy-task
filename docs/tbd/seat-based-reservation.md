# 좌석 단위 예약 전환 (설계 초안)

> 상태: **설계 초안 — 구현 전** (이슈 #41) · 방향: B. 학생이 좌석을 직접 고름
> 현재 동작은 [requirements.md 9절](../requirements.md#결정한-규칙)을 따른다. 이 문서는 바뀔 내용을 미리 정리한 것이다.

## 1. 배경

### 지금 규칙의 한계

정원은 **자습실 단위**다(규칙 #2, 명세의 "자습실별 신청 인원(취소 제외)은 최대 인원을 넘을 수 없다"). 신청·대기 동기화·목록이 모두 `status = 'APPLIED'`인 신청 수만 세고 **방문 시각을 보지 않는다.** 그래서 실제 자습실 운영과 어긋나는 경우가 생긴다.

- **끝난 방문도 자리를 차지한다.** 18~20시 학생의 방문이 끝나도 신청은 `APPLIED`로 남아 정원 1자리를 계속 쓴다. 자리가 나는 경우는 시작 전 취소, 학생 삭제, 정원 증가뿐이다.
- **시간이 겹치지 않아도 정원을 나눠 쓴다.** 정원 1자리 자습실에서 10~12시 학생이 신청해 두면, 저녁 19~21시는 비어 있는데도 마감으로 보인다.

### 레퍼런스

좌석 배치도로 자습실을 관리하는 화면(번호가 붙은 좌석, 재석·공석·특이사항)을 참고했다. 이 화면에는 두 가지 성격이 섞여 있다.

| 성격             | 내용                                                            | 이번 범위                                                                                       |
| ---------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 좌석 지정        | 자습실에 번호가 붙은 좌석이 정해져 있고 학생이 특정 좌석을 쓴다 | **포함**                                                                                        |
| 실시간 재석 관리 | 재석·외출·쪽잠·이탈·조퇴 등 "지금 실제로 있는지"                | **제외** — 입실·퇴실 체크(출결)가 있어야 나오는 정보. 지금 시스템은 "언제 오기로 했는지"만 안다 |

## 2. 방향 비교

|                   | A. 시간대별 정원              | **B. 좌석 직접 선택 (채택)**                         | C. 좌석 자동 배정                  |
| ----------------- | ----------------------------- | ---------------------------------------------------- | ---------------------------------- |
| 정원 규칙         | 구간 안 동시 인원 ≤ 최대 인원 | **같은 좌석의 시간 겹침 금지** (최대 인원 = 좌석 수) | B와 같음, 좌석은 서버가 배정       |
| 18~20시 → 20~22시 | 가능                          | 가능                                                 | 가능                               |
| 학생 경험         | 시간만 고름                   | 시간 + **좌석 선택**(배치도)                         | 시간만 고르고 좌석 번호를 안내받음 |
| 강사 경험         | 시간대별 인원                 | **시각별 좌석 배치도**                               | 시각별 좌석 배치도                 |
| 스키마            | 변경 없음                     | 좌석 테이블, 신청에 좌석                             | B와 같음                           |
| 규모              | 중간                          | **큼**                                               | 큼 (B보다 작음)                    |

B를 고른 이유: 실제 자습실·독서실처럼 "몇 번 좌석"을 학생이 정하고, 강사는 좌석 배치도로 현황을 본다. 시간대별 정원 문제(1절)도 함께 해결된다.

### B에서 새로 생기는 성질: 좌석 단편화

좌석 방식은 시간대별 정원(A)보다 **엄격하다.** 좌석 2개 중 1번 좌석이 18~20시, 2번 좌석이 20~22시로 예약돼 있으면, 19~21시는 매 순간 한 자리씩 비어 있어 A로는 신청할 수 있다. 하지만 **19~21시 내내 비어 있는 좌석이 하나도 없어서** B로는 신청할 수 없다. 실제 독서실처럼 "한 자리에 계속 앉는다"는 규칙이다. 학생 화면은 고른 시간 내내 비어 있는 좌석만 고를 수 있게 하고, 없으면 시간을 바꾸거나 대기하도록 안내한다.

## 3. 바뀌는 규칙

| 구분           | 지금                                                                                                                           | 좌석 방식                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 신청 단위      | (자습실, 시간)                                                                                                                 | (자습실, **좌석**, 시간)                                                    |
| 정원 (#2)      | 자습실별 유효 신청 수 ≤ 최대 인원                                                                                              | **같은 좌석의 유효 신청끼리 시간 구간이 겹치면 안 됨.** 최대 인원 = 좌석 수 |
| 정원 축소 (#7) | 유효 신청 수보다 작게 금지                                                                                                     | 좌석을 줄일 때 **미래 예약이 있는 좌석은 없앨 수 없음** (미정 2)            |
| 시간 수정      | 정원 검사 없음 (인원이 그대로라서)                                                                                             | **같은 좌석이 새 시간에도 비어 있어야 함** (좌석 변경 허용 여부는 미정 5)   |
| 대기열 (#14)   | 자습실에 빈자리가 나면 순번대로 제안                                                                                           | 원하는 시간 내내 비어 있는 좌석이 생기면 그 좌석을 잡아 제안 (미정 3)       |
| 그대로         | 자습실당 학생 1건(#3), 같은 학생의 시간 겹침 금지(#13), 운영 기간·과거 시간 규칙(#1·#6), 시작한 방문 수정 불가(#12), 자습실 락 | —                                                                           |

명세의 "최대 인원"은 **"좌석 수"로 해석**한다. 실제 자습실은 좌석 단위로 운영되고, 동시에 앉을 수 있는 최대 인원이 곧 좌석 수이기 때문이다. 이 해석은 README의 정한 규칙 #2에 근거와 함께 남긴다.

## 4. 바뀌는 곳

### 4-1. DB (스키마·마이그레이션)

| 대상               | 변경                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `seats` (신규)     | `id`, `study_room_id`, `number`(좌석 번호, 자습실 안에서 유일), 격자 위치(`row`·`col` 또는 순서), `created_at`, 필요하면 `deleted_at` |
| `study_rooms`      | 배치 정보(열 수) 추가. `max_personnel`과 좌석 수의 관계는 미정 1                                                                      |
| `visits`           | `seat_id` 추가 — 처음엔 NULL 허용으로 추가 → 기존 데이터 이전 → NOT NULL                                                              |
| `visit_histories`  | `prev_seat_id`, `seat_id` — "3번 → 5번 좌석" 변경도 이력으로                                                                          |
| `waitlist_entries` | 제안이 잡아 둔 좌석(`offered_seat_id`), 특정 좌석 대기라면 원하는 좌석 (미정 3)                                                       |
| 인덱스             | `visits (seat_id, status, start_at)` — 좌석별 겹침 조회                                                                               |

- **같은 좌석 겹침 금지는 DB 제약이 아니라 서비스 로직**으로 검사한다. 배제 제약(`EXCLUDE USING gist`)은 Prisma 스키마로 표현할 수 없어, PostgreSQL이 조건을 다른 형태로 저장하면 드리프트가 생긴다(#31·#36에서 확인).
- **기존 데이터 이전 마이그레이션** (가장 까다로운 부분)
  1. 기존 자습실마다 좌석 1~`max_personnel`번을 만든다.
  2. 기존 유효 신청을 방문 시작 순으로 보며, 시간이 겹치지 않는 가장 작은 번호 좌석에 배정한다. 지금은 유효 신청 수 ≤ 최대 인원이 보장되므로 모두 배정할 수 있다.
  3. 취소된 신청은 마지막으로 신청했던 시점에 맞춰 같은 방식으로 배정하거나, 좌석 없이(NULL) 둔다. 이 경우 재신청할 때 좌석을 다시 고른다.
  4. `seat_id`를 NOT NULL로 바꾼다. 취소 신청을 NULL로 두기로 하면 "유효 신청은 좌석 필수"를 서비스 로직으로 보장한다.

### 4-2. 공유 타입 (`packages/shared`)

- 신규 타입: `Seat { id, number, row, col }`, 좌석별 예약 현황(그 시간에 비어 있는지, 예약자)
- 좌석 필드 추가: `Visit`·`StudyRoomVisit`·`StudyRoomHistory`(이전·이후 좌석)·`WaitlistEntry`(제안 좌석)
- 요청: `CreateVisitRequest`·`UpdateVisitRequest`에 `seatId`
- `StudyRoom.availableSeats`(숫자 하나)는 시간마다 달라지므로 의미를 다시 정한다 (미정 4)
- 에러 코드: `SEAT_TAKEN`(그 시간에 이미 예약된 좌석), `SEAT_NOT_FOUND`, `SEATS_IN_USE`(예약이 있는 좌석은 줄일 수 없음)

| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| 매퍼·DTO·Swagger           | 좌석 필드                                                                                                                                                                                               |
| 락                         | **변경 없음.** 자습실 행 락이 그 자습실의 모든 좌석 작업을 차례로 처리하므로 같은 좌석 동시 예약도 막힌다. 락 순서(학생 → 자습실)도 그대로                                                              |

1번의 자동 배정은 이후 "아무 좌석이나" 선택지로도 쓸 수 있다.

## 7. 범위 밖

- **실시간 재석 관리** (레퍼런스의 재석·외출·쪽잠·이탈·조퇴): 입실·퇴실 체크와 출결 상태가 필요한 별도 도메인
- **좌석 배치 편집기** (통로·벽·출입문을 그리는 자유 배치): 미정 6에서 ②로 정하면 다시 검토
- **좌석 속성** (창가, 콘센트 등)과 선호 좌석 추천

## 8. 위험

- **변경 범위가 넓다.** DB·API·웹·테스트·문서가 모두 바뀐다. 그래서 단계별 PR로 나누고, 1번 PR의 자동 배정으로 중간 상태에서도 앱이 동작하게 한다.
- **기존 데이터 이전**: 운영 데이터가 있다는 가정에서 마이그레이션이 실패하지 않도록, 배정 로직을 테스트 DB에서 먼저 검증한다.
- **명세와의 거리**: "최대 인원 = 좌석 수"는 해석이다. 평가자가 읽을 수 있게 근거를 README에 남긴다.
- **좌석 단편화**: 시간대별 정원보다 받을 수 있는 신청이 줄어든다. 학생 화면에서 "그 시간 내내 비어 있는 좌석이 없어요 → 시간을 바꾸거나 대기"로 분명히 안내해야 한다.
