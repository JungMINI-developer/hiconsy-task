# 과제 요구사항 명세

하이컨시 사전과제 원문 명세를 정리한 문서입니다. 설계와 구현 범위는 이 문서를 기준으로 정합니다.

## 1. 배경

> 자습실 예약을 아직도 단톡방으로 받고 있대요. 이거 시스템으로 만들어 줄 수 있어요? — PM

| 화자 | 현장의 목소리                                         | 해결할 문제                    |
| ---- | ----------------------------------------------------- | ------------------------------ |
| 강사 | "자습실 열 때마다 공지 올리고 인원 세는 게 일이에요." | 자습실 공개와 정원 관리 자동화 |
| 학생 | "신청은 했는데 제가 명단에 있는 건지 모르겠어요."     | 본인 신청 상태 확인            |
| 학생 | "7시에 가기로 했는데 8시로 바꾸려면 누구한테 말해요?" | 학생이 직접 방문 시간 수정     |

- 목표: **핵심 기능 MVP**를 빠르게 만들고, 피드백을 받으며 확장할 수 있도록 **확장을 고려한 설계**를 한다.
- 모든 요구사항을 만족할 필요는 없으며, 구현 범위는 지원자 재량이다.

## 2. 자습실 운영 규칙

| 항목      | 규칙                                                                                        |
| --------- | ------------------------------------------------------------------------------------------- |
| 자습실    | 강사가 최대 인원과 운영 기간(시작~종료 일시)을 정해 공개한다                                |
| 방문 신청 | 학생이 자습실 운영 기간 안에서 방문 시간을 정해 신청한다                                    |
| 정원      | 자습실별 신청 인원(취소 제외)은 최대 인원을 넘을 수 없다                                    |
| 중복 신청 | 같은 학생은 한 자습실에 한 건만 신청할 수 있다                                              |
| 수정·취소 | 학생은 본인 신청의 방문 시간을 수정하거나 취소할 수 있다. 신청·수정·취소 이력은 모두 남는다 |
| 삭제      | 삭제된 자습실에는 신청할 수 없다                                                            |

## 3. 역할

| 역할 | 권한                                                  |
| ---- | ----------------------------------------------------- |
| 강사 | 자습실 등록·수정·삭제, 신청 이력 조회, 학생 목록 조회 |
| 학생 | 방문 신청·시간 수정·취소                              |

> 로그인은 생략할 수 있습니다. 화면에서 강사/학생을 고르는 방식이면 충분합니다.

## 8. 제출 조건

1. 평가자의 로컬 환경에서 코드 실행과 테스트가 가능해야 한다.
2. 제출 메일에 GitHub 저장소 링크를 포함한다.
3. 저장소에 README.md를 작성한다 (문서 디렉터리는 선택).
   - 프로젝트 실행 방법 (필수)
   - 사용한 기술 스택 및 선택 이유 (필수)
   - 아키텍처(인프라, 소스 코드) 및 컨벤션 (필수)
   - 데이터베이스 스키마 구조 및 설계 이유 (필수)
   - 개발 시 고민했던 점 또는 아쉬운 점 (선택)
4. 규칙 해석이 애매한 부분은 **본인이 정한 규칙을 README에 적는다.**

## 9. 해석이 필요한 부분

명세만으로는 정해지지 않아 직접 규칙을 정한 항목입니다. 확정된 규칙은 README의 "정한 규칙"에도 옮깁니다.

### 결정한 규칙

| #   | 항목                | 결정                                                                                                                                                      |
| --- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 방문 시간의 형태    | **시작~종료 구간**으로 신청한다. 구간 전체가 자습실 운영 기간 안에 있어야 한다                                                                            |
| 2   | 정원 기준           | **자습실 단위 정원**. 자습실별 유효 신청(취소 제외) 수가 `maxPersonnel`을 넘을 수 없다                                                                    |
| 3   | 재신청              | 취소한 뒤 같은 자습실에 **다시 신청할 수 있다**. 중복 금지는 "유효 신청 1건" 기준이다                                                                     |
| 4   | 이력 저장 방식      | **신청 테이블과 이력 테이블을 분리**한다. 신청은 현재 상태, 이력은 신청·수정·취소 이벤트를 쌓는다                                                         |
| 5   | 정원 동시성         | 신청·수정 시 **트랜잭션 + DB 락**으로 정원 검사와 저장을 원자적으로 처리한다                                                                              |
| 7   | 최대 인원 축소      | 현재 유효 신청 인원보다 작게 줄이면 **막는다** (409 `CAPACITY_BELOW_CURRENT`). 같은 값까지는 허용                                                         |
| 8   | 운영 기간 변경      | 유효 신청의 방문 구간이 새 기간 밖으로 벗어나면 **막는다** (409 `PERIOD_EXCLUDES_VISITS`)                                                                 |
| 9   | 자습실 삭제         | **허용하고 유효 신청을 자동 취소**한다. 이력에 `actorType = SYSTEM`, 사유 "자습실 삭제"를 남긴다                                                          |
| 10  | 학생 삭제·전화번호  | 삭제 시 **유효 신청 자동 취소** (`SYSTEM`, "학생 삭제"). 전화번호는 **삭제되지 않은 학생끼리 중복 불가**, 휴대폰 번호만 허용하고 `010-1234-5678`로 정규화 |
| 6   | 과거 시간 신청      | 방문 시작 시각이 **현재 이후**여야 신청·수정할 수 있다 (400 `VISIT_IN_PAST`)                                                                              |
| 11  | 신청 주체 식별      | 로그인 대신 **경로의 학생 id**를 본인으로 본다 (`/api/students/:studentId/visits`). 다른 학생의 신청은 404 `VISIT_NOT_FOUND`                              |
| 12  | 수정·취소 가능 시점 | **이미 시작된 방문**(시작 시각 ≤ 현재)은 수정·취소할 수 없다 (409 `VISIT_ALREADY_STARTED`)                                                                |

> 7·8번은 학생이 모르는 사이 신청이 취소되지 않도록 막고, 강사가 먼저 학생과 조율하게 한다.
> 9번은 강사의 명시적인 의도이므로 허용하되, 학생이 이력으로 사유를 확인할 수 있게 한다.
> 10번의 전화번호는 학생을 구분하는 실질적인 식별자라 중복을 막되, 삭제된 학생의 번호는 재사용할 수 있게 부분 유니크 인덱스로 처리한다.
> 6·12번은 이미 지나간 사실(방문)을 바꾸지 못하게 해 이력과 실제가 어긋나지 않도록 한다.
> 11번에서 다른 학생의 신청을 403이 아닌 404로 응답하는 것은 해당 신청이 존재하는지조차 노출하지 않기 위해서다.
