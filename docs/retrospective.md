# 개발 시 고민한 점 / 아쉬운 점

> README [5. 개발 시 고민한 점 / 아쉬운 점](../README.md#5-개발-시-고민한-점--아쉬운-점)의 상세판입니다.

## 고민한 점

### 평가 환경에서의 실행 재현성

- 로컬 실행 요구사항을 만족하기 위해 배포 대신 Docker Compose 전체 실행을 기본 방법으로 제공했습니다.
- Node/pnpm 버전에 의존하지 않도록 하고, 마이그레이션·시드를 컨테이너 시작 시 자동 적용했습니다.

### FE/BE 응답 계약 통일

- `packages/shared`에 응답 타입을 두고, BE에서는 Interceptor/Exception Filter로 모든 응답을 그 포맷에 맞췄습니다.

### 신청(현재 상태)과 이력(이벤트)을 나누기

- "신청·수정·취소 이력은 모두 남는다"와 "정원·중복 검사"는 필요한 데이터 모양이 다릅니다. 이력만 쌓고 최신 행을 현재 상태로 쓰면 정원 계산마다 학생별 최신 행을 찾아야 하고, 유니크 제약으로 중복을 막을 수 없습니다.
- 그래서 `visits`(현재 상태)와 `visit_histories`(append-only 이벤트)를 나누고, 같은 트랜잭션에서 함께 씁니다. 취소 후 재신청은 새 행이 아니라 기존 행을 `APPLIED`로 되돌려, `UNIQUE(student_id, study_room_id)` 하나로 중복 방지와 재신청을 함께 해결했습니다. → [database.md](./database.md)

### 정원 동시성: 트랜잭션만으로는 막히지 않는다

- 신청은 "인원 세기 → 저장"이라, 두 요청이 동시에 세면 둘 다 통과합니다. 트랜잭션(READ COMMITTED)만으로는 막히지 않아 **자습실 행을 `FOR UPDATE`로 잠근 뒤** 세도록 했습니다.
- 테스트가 정말 경쟁 상태를 잡는지 확인하려고 락을 빼고 돌려 봤습니다. 정원 3명에 10명이 동시에 신청하면 10명 전원이 성공해 테스트가 실패했고, 1자리 남은 자습실에 150명이 몰리면 4명이 성공(8/5명)했습니다. 락이 있으면 남은 자리 수만큼만 성공합니다.
- "네트워크가 빠른 사람이 먼저 되는가?"라는 질문에서, **동시성 제어(정확성)와 공정성(정책)을 구분**했습니다. 락은 "정확히 남은 자리만큼만 성공"을 보장하고, 누가 이기는지는 서버 도착 기준 선착순입니다. 단톡방 선착순을 옮긴 서비스라 선착순을 유지하고, 공정성이 더 중요해지면 추첨·대기열 같은 정책으로 확장하도록 정리했습니다. → [solutions/study-room-capacity-concurrency.md](./solutions/study-room-capacity-concurrency.md)

### 시간 겹침 규칙과 락 모드

- 실제로 써 보니 같은 학생이 **다른 자습실**의 같은 시간을 함께 신청할 수 있었습니다. 명세는 "한 자습실에 한 건"만 말하지만, 한 사람이 두 곳에 있을 수 없고 겹친 신청이 다른 학생의 자리를 차지하므로 규칙 #13으로 막았습니다.
- 자습실이 다르면 자습실 락이 달라 동시 요청을 못 막으므로 **학생 행을 잠가야** 했습니다. 처음 떠올린 `FOR UPDATE`는 자습실 삭제가 이력을 넣을 때 FK 검사가 거는 `FOR KEY SHARE`와 충돌해 교착 상태를 만들었습니다(테스트로 `deadlock detected` 재현). 그래서 같은 학생끼리는 직렬화하면서 FK 검사와는 충돌하지 않는 `FOR NO KEY UPDATE`를 골랐습니다.
- DB 배제 제약(`EXCLUDE USING gist`)도 검토했지만 Prisma 스키마로 표현할 수 없어, 정원과 같은 방식(트랜잭션 + 행 락)으로 맞췄습니다. → [solutions/visit-time-overlap-concurrency.md](./solutions/visit-time-overlap-concurrency.md)

### 강사의 변경이 학생 신청을 깨뜨릴 때 (FR-ROM-06)

- 정원 축소와 운영 기간 변경은 **막고**(409), 자습실 삭제는 **허용하고 자동 취소**했습니다. 축소·변경은 학생이 모르는 사이 신청이 사라지게 하므로 강사가 먼저 학생과 조율하게 했고, 삭제는 강사의 명시적 의도라 허용하되 학생이 취소됨 탭에서 사유("자습실 삭제")를 볼 수 있게 했습니다.

### 화면은 막고, 판단은 서버가

- 운영 기간 밖·지난 시각·내 신청과 겹치는 시각은 선택지에서 미리 막아 헛걸음을 줄였습니다. 그래도 화면의 데이터는 낡을 수 있어(다른 탭, 다른 학생의 신청) 최종 판단은 항상 서버가 하고, 화면은 에러 코드별로 "알리고 다시 조회"하도록 나눴습니다.
- 정원이 방금 차서 거절된 학생을 위해 대기열과 "다른 자습실 안내"를 비교했습니다. 대기열을 자동 확정으로 만들면 시간 겹침 규칙과 충돌하고, 락 순서(학생 → 자습실)가 뒤집히며, 알림이 없어 확정된 줄 모른다는 문제가 있었습니다. 그래서 먼저 **같은 시간에 자리가 남은 자습실로 이어서 신청**하게 하고(#35), 대기열은 본인이 확정하는 "자리 제안" 방식으로 만들었습니다(#36).

### 대기열: 자리 제안과 지연 동기화 (#36, #44에서 제거)

> 좌석 단위 예약으로 전환하며 대기열을 뺐습니다(#44). 좌석과 시간을 직접 고르면 대부분 다른 좌석·시간으로 신청하면 되고, 좌석 단위 대기는 규칙이 크게 복잡해지기 때문입니다. 아래는 만들 때의 기록입니다.

- 대기열은 "자리가 나면 순번대로 10분짜리 제안 → 본인 확정"으로 만들었습니다. 제안 중인 자리는 정원에 넣어 다른 학생이 가로채지 못하게 하고, 대기자가 있으면 새 신청자에게는 마감으로 보이게 했습니다(대기자 우선).
- 스케줄러 없이 **자습실을 건드리는 작업마다 자습실 락 안에서 대기열을 맞추는** 방식을 골랐습니다. 자리를 가져가려는 모든 신청이 먼저 동기화하므로, 만료된 제안이 정리되기 전에 자리가 새 신청자에게 넘어가는 일은 없습니다.
- 구현하면서 놓치기 쉬운 함정이 두 가지 있었습니다.
  - 신청 트랜잭션 안에서 다음 대기자에게 제안을 만든 뒤 `CAPACITY_FULL`로 거절하면, 롤백으로 그 제안까지 사라집니다. 그래서 거절될 수 있는 작업은 별도 트랜잭션에서 먼저 동기화해 커밋했습니다.
  - "진행 중 대기 1건" 부분 유니크 인덱스를 `status IN (...)`으로 만들었더니, PostgreSQL이 조건을 다른 형태로 저장해 Prisma가 매번 스키마와 DB가 다르다고 판단했습니다. `ended_at IS NULL`로 바꿔 해결했습니다.
- 학생 삭제가 자습실 락을 잡게 되면서, 회고에 "검증하지 못한 경로"로 적어 둔 학생 삭제 ↔ 자습실 삭제 교착 상태가 실제 문제가 됐습니다. 학생 삭제의 락을 `FOR NO KEY UPDATE`로 바꿔 해소했고, `FOR UPDATE`로 되돌리면 테스트가 500으로 실패하는 것까지 확인했습니다. → [solutions/waitlist-offer.md](./solutions/waitlist-offer.md)
- 대기열을 뺄 때(#44) 학생 삭제의 자습실 락도 대기열용이라 함께 뺐다가, 교착 상태 테스트가 다시 500으로 실패했습니다. 그 락은 "같은 신청을 둘 다 취소하는 학생 삭제 ↔ 자습실 삭제"도 막고 있었습니다. 기능을 걷어낼 때도 그 기능이 들여온 락·검사가 다른 문제를 함께 막고 있는지 테스트로 확인해야 한다는 걸 배웠습니다.

### 명세를 글자 그대로 구현한 뒤 해석을 바꾸기: 좌석 단위 예약 (#45)

- 처음엔 정원을 명세 문장 그대로 "자습실별 유효 신청 수 ≤ 최대 인원"으로 만들었습니다. 써 보니 끝난 방문도 계속 자리를 차지하고, 오전 학생과 저녁 학생이 시간이 겹치지 않아도 정원을 나눠 써서 비어 있는 저녁까지 마감으로 보였습니다.
- 시간대별 정원(동시 인원), 좌석 직접 선택, 좌석 자동 배정을 비교해 **좌석 직접 선택**을 골랐습니다. 실제 자습실처럼 "몇 번 좌석"을 학생이 정하고 강사는 배치도로 보는 쪽이 현장 문제("명단에 있는지 모르겠다")와도 맞았습니다. 명세의 "최대 인원"은 **좌석 수**로, "신청 인원"은 **같은 시각에 있는 인원**으로 해석하고 근거를 requirements 9절 #2에 남겼습니다.
- 바꾸는 범위가 커서 설계 문서(`docs/tbd`)로 결정을 먼저 확정하고, 대기열 제거(#44) → 좌석 모델·API(#48) → 학생 화면(#50) → 강사 화면(#52) → 문서 순으로 나눴습니다. 기존 데이터는 마이그레이션에서 유효 신청마다 겹치지 않는 가장 작은 번호 좌석을 배정해 옮겼습니다.
- **락 구조는 바꾸지 않았습니다.** 같은 좌석 동시 예약도 자습실 행 락 안에서 "좌석 겹침 검사 → 저장"을 하면 막힙니다. 락을 빼면 같은 좌석에 10명이 모두 예약되는 것을 다시 확인했습니다. → [solutions/seat-reservation-concurrency.md](./solutions/seat-reservation-concurrency.md)
- 강사 목록에 처음엔 명세의 "현재 신청 인원"을 유효 예약 건수로 보여줬는데, 좌석을 시간별로 나눠 쓰니 `10석 · 예약 14건`처럼 정원을 넘은 것처럼 읽혔습니다. 해석 #2에 맞춰 **지금 이용 중인 좌석**으로 바꿨습니다(#52). 규칙을 바꾸면 화면의 숫자도 같은 기준으로 읽혀야 한다는 걸 배웠습니다.

### 조기 퇴실과 "지금"의 기준 (#66, #69)

- 시작한 방문은 바꾸지 못하게 했더니(규칙 #12), 일찍 나가도 좌석이 원래 종료까지 묶였습니다. 종료 시각을 퇴실 시각으로 줄이는 **퇴실**(규칙 #16)을 더했습니다. 지난 시간은 그대로 두고 앞으로만 줄이므로 "지나간 사실은 바꾸지 않는다"는 원칙과도 맞습니다.
- 퇴실은 30분 경계가 아닌 시각에 끝나서, 그동안 드러나지 않던 차이가 생겼습니다. 강사 상세의 기본 시각은 "지금을 30분 단위로 내린 시각"이라 방금 나간 학생이 남아 보였고, 목록 카드("지금 1석")와 숫자가 달랐습니다. "지금" 칸은 실제 현재 시각으로 조회하도록 바꿨고, 퇴실 시각을 초 단위로 저장해 화면이 보내는 조회 시각과 정밀도를 맞췄습니다(회귀 테스트가 320px에서만 반복 실패해 찾았습니다).

### 직접 써 보며 다듬기

- 기능을 다 만든 뒤 Playwright로 강사·학생 흐름을 실제로 눌러 보며 점검했습니다. 토스트가 좁아 시간 표기가 끊기는 문제, 학생 화면의 정원 막대가 "남은 자리"와 반대로 읽히는 문제, 동명이인 신청자를 구분할 수 없는 문제 등을 찾아 고치고 E2E로 고정했습니다. 320px 화면도 함께 검증합니다.
- 제출 전에는 **평가자와 같은 조건**(GitHub에서 새로 clone → `docker compose up --build` → 시드 데이터)에서 브라우저로 전체 기능을 다시 점검했습니다. 개발 환경에서는 보이지 않던 문제가 나왔습니다.
  - Docker의 api 컨테이너는 UTC라, 시드가 "오늘 0시"를 실행 환경 시간대로 계산해 자습실 시각이 9시간 밀렸습니다(#55). KST로 직접 계산하도록 고쳤습니다.
  - 학생 헤더에 "내 신청" 개수 배지가 붙으면 320px에서 헤더가 넘쳤습니다(#63). E2E는 신청이 없는 상태만 검사해 놓쳤습니다.

## 아쉬운 점

- **인증이 없습니다.** 명세가 허용한 대로 화면에서 역할과 학생을 고르고, API는 경로의 학생 id를 본인으로 봅니다. 다른 학생의 id로 요청하면 그 학생으로 신청할 수 있으므로, 실서비스라면 로그인과 소유권 검증이 먼저 필요합니다.
- **알림이 없습니다.** 자습실 삭제로 신청이 자동 취소돼도 학생은 앱을 열어야 압니다.
- **좌석 단편화가 있습니다.** 좌석 방식은 "한 자리에 계속 앉는다"는 규칙이라, 매 순간 한 자리씩 비어 있어도 그 시간 내내 빈 좌석이 없으면 신청할 수 없습니다(1번 좌석 18~20시, 2번 좌석 20~22시 예약 → 19~21시 불가). 화면은 다른 시간·다른 자습실을 안내하지만, 구간을 나눠 좌석을 옮겨 앉는 예약은 만들지 않았습니다.
- **실제 재석은 모릅니다.** 좌석 배치도는 "언제 오기로 했는지"(예약)만 보여줍니다. 입·퇴실 체크가 없어 재석·외출·조퇴 같은 실제 상태는 보여줄 수 없습니다.
- **고부하는 150명까지만 확인했습니다.** 한 자습실에 수백~수천 건이 몰리면 락보다 커넥션 풀·트랜잭션 대기 시간이 먼저 한계가 됩니다. (학생 삭제 ↔ 자습실 삭제 교착 상태는 #36에서 해소했습니다.)
- **이력 생성 로직이 네 곳에 나뉘어 있습니다.** 신청·변경·취소·퇴실이 각자 이력을 만듭니다. 공통화(#12)를 검토했지만, 1건짜리 함수로 묶으면 시스템 일괄 취소가 신청 수만큼 쿼리를 쓰게 되어 하지 않았고, 겹치던 취소 이력 모양만 한 함수로 모았습니다(#57).
