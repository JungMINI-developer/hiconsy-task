# 대기열: 정원 마감 시 대기 등록과 자리 제안

> 관련: 이슈 #36 · 규칙 [requirements.md 9절 #14](../requirements.md#결정한-규칙) · 앞선 문서: [정원 동시성](./study-room-capacity-concurrency.md), [시간 겹침](./visit-time-overlap-concurrency.md)

## 1. 문제

정원이 찬 자습실에서 신청이 거절된 학생은 다른 자습실을 찾거나(#35) 포기할 수밖에 없었다. 누군가 취소해 자리가 나도 그 사실을 알 수 없고, 마침 그 순간 들어온 다른 학생이 자리를 가져간다. 먼저 원했던 학생이 손해를 본다.

## 2. 결정한 정책

| 항목              | 결정                                                                                                                        | 이유                                                                                                        |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 방식              | **자리 제안**: 자리가 나면 다음 순번에게 제안하고, **본인이 확정**                                                          | 자동 확정은 시간 겹침 규칙과 충돌하고, 락 순서가 뒤집히며, 알림이 없어 확정된 줄 모른다 (아래 3절)          |
| 대기 시 시간      | 원하는 방문 시간을 함께 저장, 확정할 때 바꿀 수 있음                                                                        | 제안을 "내일 10:00–12:00 자리가 났어요"처럼 구체적으로 보여줄 수 있다. 방문 시작이 지나면 대기는 자동 종료  |
| 제안 유효 시간    | **10분** (단, 방문 시작 전까지)                                                                                             | 자리를 오래 묶어 두지 않는다                                                                                |
| 만료              | 대기 종료, 다음 순번에게 제안. 다시 대기하려면 새로 등록(맨 뒤)                                                             | 응답하지 않는 학생이 자리를 계속 붙잡지 않게                                                                |
| 정원              | **유효 신청 + 만료 전 제안**                                                                                                | 제안받은 학생의 자리를 다른 학생이 가로채지 못하게                                                          |
| 빈자리 우선순위   | **대기자 우선** — 대기자가 남아 있으면 새 신청자에게는 마감                                                                 | 줄을 선 사람이 손해 보지 않게. 학생 화면의 남은 자리도 대기자 수를 뺀 값(`availableSeats`)                  |
| 대기 중 다른 신청 | **백업으로 허용** — 같은 시간에 다른 자습실 신청 가능                                                                       | 대기는 확정이 아니다. 제안이 오면 겹친 신청을 취소하거나 다른 시간을 골라 확정(시간 겹침 규칙 #13은 그대로) |
| 강사 변경         | 기간 밖이 된 대기·삭제된 자습실의 대기는 자동 취소. 정원을 줄여 제안이 넘치면 늦게 등록한 제안부터 대기로 되돌림(순번 유지) | 대기는 약속이 아니므로 강사의 변경을 막지 않는다                                                            |
| 학생 삭제         | 그 학생의 대기 자동 취소, 비워진 신청 자리는 다음 대기자에게                                                                |                                                                                                             |

## 3. 왜 자동 확정이 아닌가

취소 트랜잭션 안에서 다음 대기자를 바로 `APPLIED`로 올리는 방식을 먼저 검토했다.

1. **시간 겹침 규칙(#13)과 충돌**: 대기 중에 다른 자습실의 같은 시간을 신청했다면 자동 확정 시 겹치는 신청이 생긴다. 대기가 시간을 차지한다고 보면, 언제 풀릴지 모르는 대기 때문에 다른 선택지가 막힌다.
2. **락 순서 역전**: 취소 트랜잭션은 이미 자습실 락을 잡고 있다. 대기자의 겹침을 검사하려면 그 학생의 락이 필요한데, 기존 순서(학생 → 자습실)와 반대가 되어 교착 상태 위험이 생긴다.
3. **학생이 알 수 없음**: 로그인·알림이 없어, 자동으로 확정돼도 학생은 모르고 오지 않는다.

자리 제안 방식에서는 취소 트랜잭션이 **대기 행의 상태만 바꾸고**(WAITING → OFFERED), 확정은 학생이 직접 하는 **기존 신청 흐름**(학생 락 → 자습실 락 → 정원·겹침 검사)이 그대로 맡는다.

## 4. 데이터

`waitlist_entries` 1행 = 대기 1건. 종료된 대기도 지우지 않고, 같은 학생이 다시 대기하면 새 행을 만든다.

```
WAITING ──(자리가 남)──▶ OFFERED ──(신청)──▶ CONFIRMED
   │  ▲                     │  ├──(거절)──▶ DECLINED
   │  └─(정원 축소로 되돌림)──┘  └──(10분 경과)──▶ EXPIRED
   ├──(원하는 시작 지남)──▶ EXPIRED
   └──(본인 취소·자습실/학생 삭제·기간 변경)──▶ CANCELED
```

- **진행 중** = `WAITING`·`OFFERED` = `ended_at IS NULL`. 학생-자습실 쌍당 진행 중 1건은 부분 유니크 인덱스 `(student_id, study_room_id) WHERE ended_at IS NULL`로 DB가 보장한다.
  - 처음에는 `WHERE status IN ('WAITING', 'OFFERED')`로 만들었다. 그런데 PostgreSQL이 이 조건을 `status = ANY (ARRAY[...])`로 바꿔 저장해서, Prisma가 매번 스키마와 DB가 다르다고 판단했다(`migrate diff`가 비어 있지 않음). 학생 전화번호 인덱스(`deleted_at IS NULL`)와 같은 형태인 `ended_at IS NULL`로 바꿔 차이가 없어진 것을 확인했다.
- 순번은 따로 저장하지 않고 `created_at, id` 순서로 계산한다. 정원 축소로 대기로 되돌아가도 원래 순번이 유지된다.

## 5. 제안 동기화: 언제, 어떻게

`syncWaitlist(tx, room)` (`apps/api/src/waitlist/waitlist-sync.ts`) — **자습실 행 락 안에서만** 호출한다.

1. 만료: 제안 유효 시간이 지났거나 원하는 방문 시작이 지난 대기를 끝낸다 (EXPIRED)
2. 정원 축소: 유효 신청 + 제안 > 정원이면, 늦게 등록한 제안부터 WAITING으로 되돌린다
3. 빈자리 제안: 정원 − 유효 신청 − 제안만큼, 등록 순으로 WAITING → OFFERED (`offer_expires_at = min(지금 + 10분, 방문 시작)`)

호출하는 곳:

| 작업                         | 이유                                                                                    |
| ---------------------------- | --------------------------------------------------------------------------------------- |
| 방문 신청                    | 만료 정리 후 정원 검사. 대기자가 있으면 빈자리가 모두 제안되어 새 신청자는 마감         |
| 방문 취소                    | 비워진 자리를 다음 대기자에게                                                           |
| 자습실 수정                  | 정원이 늘면 제안, 줄면 넘치는 제안을 되돌림. 기간 밖 대기 취소                          |
| 학생 삭제                    | 비워진 신청 자리를 각 자습실의 다음 대기자에게                                          |
| 대기 등록·취소/거절          | 순번·자리 판단 전에 맞춤                                                                |
| 내 대기 조회, 강사 대기 조회 | 알림이 없으므로, 학생이 앱을 열 때 앞사람의 만료를 정리하고 다음 사람에게 제안이 보이게 |

스케줄러 없이 "누군가 이 자습실을 건드릴 때" 정리하는 지연 방식이다. 정확성은 지켜진다. 자리를 가져가려는 모든 시도(신청)가 먼저 동기화를 실행하므로, 만료된 제안이 정리되기 전에 자리가 새 신청자에게 넘어가는 일은 없다. 조회용 인원(`offeredCount`, `waitingCount`, `availableSeats`)은 아직 정리되지 않은 만료 제안·지난 대기를 빼고 센다.

### 함정: 거절되는 트랜잭션 안에서 동기화하면 제안이 사라진다

신청 트랜잭션 안에서 동기화(다음 대기자에게 제안)를 한 뒤 `CAPACITY_FULL`로 거절하면, **트랜잭션 롤백으로 방금 만든 제안까지 사라진다.** 그래서 409로 거절될 수 있는 작업(신청, 대기 등록)은 **별도 트랜잭션에서 먼저 동기화해 커밋**하고(`syncWaitlistNow`), 본 트랜잭션에서 한 번 더 동기화한다. 두 번째 동기화는 그 사이에 끼어든 변경을 맞추는 용도라 대부분 아무 일도 하지 않는다.

## 6. 락

| 작업                                | 학생 행                                     | 자습실 행                             |
| ----------------------------------- | ------------------------------------------- | ------------------------------------- |
| 방문 신청(제안 확정 포함)·시간 수정 | `FOR NO KEY UPDATE`                         | `FOR UPDATE`                          |
| 방문 취소, 대기 등록·취소/거절      | `FOR SHARE`                                 | `FOR UPDATE`                          |
| 자습실 수정·삭제                    | -                                           | `FOR UPDATE`                          |
| 학생 삭제                           | **`FOR NO KEY UPDATE`** (기존 `FOR UPDATE`) | 관련 자습실 전부 `FOR UPDATE` (id 순) |

- 대기 행을 바꾸는 작업은 모두 자습실 락 안에서 실행되어 순번·정원 계산이 엇갈리지 않는다.
- 동기화는 다른 학생의 대기 행 **상태만** 바꾼다. FK 컬럼이 바뀌지 않는 UPDATE는 학생 행에 `FOR KEY SHARE`를 걸지 않으므로, 다른 학생의 락을 기다리지 않는다.

### 학생 삭제 ↔ 자습실 삭제 교착 상태 해소

학생이 삭제되면 비워진 자리를 대기자에게 넘겨야 해서, 학생 삭제도 자습실 락을 잡게 되었다. 그런데 기존처럼 학생 행을 `FOR UPDATE`로 잡으면 다음처럼 서로를 기다린다. 이 경로는 [시간 겹침 문서](./visit-time-overlap-concurrency.md) 9절에 "남은 과제"로 적어 두었던 것이다.

```
학생 S 삭제                                   자습실 R 삭제
──────────────────────────────           ──────────────────────────────
학생 S  FOR UPDATE  ✅
                                         자습실 R  FOR UPDATE  ✅
자습실 R FOR UPDATE ⏳ (R 삭제를 기다림)
                                         S의 신청 자동 취소 → 이력 INSERT
                                         FK 검사: 학생 S FOR KEY SHARE ⏳ (S 삭제를 기다림)
                         ↻ 교착 상태 → PostgreSQL이 한쪽을 중단 (500)
```

학생 삭제는 키가 아닌 컬럼(`deleted_at`)만 바꾸므로 `FOR UPDATE`까지 필요 없다. `FOR NO KEY UPDATE`로 바꾸면 신청·대기 작업(`FOR SHARE`·`FOR NO KEY UPDATE`)과는 여전히 차례로 처리되지만, FK 검사(`FOR KEY SHARE`)와는 충돌하지 않아 교착 상태가 사라진다.

## 9. 한계

- **알림이 없다.** 제안은 학생이 앱을 열어야 보이고, 10분 안에 열지 않으면 다음 순번으로 넘어간다. 푸시·문자 알림이 생기면 유효 시간을 정책으로 다시 정해야 한다.
- **지연 정리**라 아무도 그 자습실을 건드리지 않으면 만료된 제안이 DB에는 OFFERED로 남는다. 정원 계산과 화면은 만료 시각으로 걸러 보므로 결과는 같고, 다음 사람에게 제안이 만들어지는 시점만 늦다(그 사람이 앱을 열 때). 즉시성이 필요해지면 스케줄러(`@nestjs/schedule`)로 주기적으로 동기화할 수 있다.
- 대기자 목록 조회가 쓰기(동기화)를 일으킨다. GET에서 상태가 바뀌는 셈이지만, 알림이 없는 구조에서 제안을 제때 만드는 가장 단순한 방법이라 택했다.
