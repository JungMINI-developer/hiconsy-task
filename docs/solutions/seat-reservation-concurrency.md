# 같은 좌석 동시 예약 처리

> 관련: 이슈 #45(#48 좌석 모델과 API, #50 학생 화면, #52 강사 화면) · 규칙 [requirements.md 9절 #2·#5·#7·#15](../requirements.md#결정한-규칙) · 설계 [tbd/seat-based-reservation.md](../tbd/seat-based-reservation.md)

## 1. 문제

좌석 단위 예약(#45)으로 바꾸며 정원 규칙이 "자습실별 유효 신청 수 ≤ 최대 인원"에서 **"같은 좌석의 유효 신청끼리 시간이 겹치면 안 됨"** 으로 바뀌었다. 학생이 좌석을 직접 고르므로, 여러 학생이 **같은 좌석·같은 시간**을 거의 동시에 고르는 일이 생긴다.

- 화면에서 비어 있던 좌석이 신청 순간에는 이미 다른 학생의 것일 수 있다.
- 서버도 "그 좌석이 비었는지 확인 → 저장"을 두 요청이 동시에 하면 둘 다 "비었다"고 보고 같은 좌석을 두 번 예약할 수 있다.

## 2. 규칙

| 항목      | 결정                                                                                                                          |
| --------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 겹침 정의 | 같은 좌석의 유효 신청(APPLIED)끼리 반열린 구간 `[start, end)`이 겹치면 안 됨. 18~20시 다음 20~22시는 같은 좌석에 앉을 수 있음 |
| 쓰는 좌석 | 자습실의 좌석 1~`max_personnel`번. 최대 인원을 줄여 번호가 더 커진 좌석은 고를 수 없음 (404 `SEAT_NOT_FOUND`)                 |
| 거절      | 고른 좌석이 그 시간에 이미 예약됨 → 409 `SEAT_TAKEN`                                                                          |
| 적용 시점 | 신청 · 재신청 · 시간·좌석 변경 (변경 시 자기 신청은 비교에서 제외)                                                            |
| 자동 배정 | `seatId`를 보내지 않으면 그 시간 내내 빈 가장 작은 번호 좌석 (호환용, 없으면 409 `CAPACITY_FULL`). 웹은 항상 좌석을 보냄      |

## 3. 방법: 자습실 행 락을 그대로 쓴다

좌석 검사는 모두 **자습실 행 `FOR UPDATE` 락 안에서** 한다(`apps/api/src/seats/seat-occupancy.ts`).

1. 트랜잭션 시작, 학생 행 `FOR NO KEY UPDATE`(같은 학생의 시간 겹침, [visit-time-overlap-concurrency.md](./visit-time-overlap-concurrency.md)) → 자습실 행 `FOR UPDATE`
2. 고른 좌석이 그 자습실의 쓰는 좌석인지 확인
3. 그 좌석에 `start_at < 새 종료 AND end_at > 새 시작`인 유효 신청이 있는지 확인 (`visits (seat_id, status, start_at)` 인덱스)
4. `visits`·`visit_histories`(이전·이후 좌석 포함) 저장, 커밋

같은 자습실의 신청은 3단계까지 차례로 들어오므로, 먼저 락을 잡은 요청이 저장하고 나면 다음 요청은 그 예약을 보고 `SEAT_TAKEN`으로 거절된다. 좌석 전환 전과 **락 구조가 같다**. 바뀐 것은 락 안에서 하는 검사(인원 세기 → 좌석 겹침 찾기)뿐이다.

## 4. 검토한 다른 방법

| 방법                                                                                                                 | 장점                                            | 고르지 않은 이유                                                                                                                                                                     |
| -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **자습실 행 락 (채택)**                                                                                              | 이미 있는 락을 그대로 씀. 락 순서가 바뀌지 않음 | 같은 자습실의 다른 좌석 신청도 차례로 처리된다. 자습실 하나가 30석 이하라 기다림이 짧다                                                                                              |
| 좌석 행 락 (`seats ... FOR UPDATE`)                                                                                  | 다른 좌석 신청은 서로 기다리지 않음             | 좌석 축소(여러 좌석을 함께 봄)·기간 변경·자습실 삭제와 순서를 맞추려면 결국 자습실 락도 잡아야 한다. 좌석을 바꾸는 변경은 두 좌석을 잠가야 해 교착 상태를 따로 따져야 한다           |
| DB 배제 제약 (`EXCLUDE USING gist (seat_id WITH =, tstzrange(start_at, end_at) WITH &&) WHERE (status = 'APPLIED')`) | DB가 직접 보장, 락이 필요 없음                  | `btree_gist` 확장이 필요하고 Prisma 스키마로 표현할 수 없다. 마이그레이션 SQL로만 관리하면 스키마와 DB가 어긋났다고 판단할 위험이 있다(#31·#36에서 확인). 학생 시간 겹침과 같은 이유 |
| 낙관적 처리 (저장 후 겹침을 다시 확인하고 되돌림)                                                                    | 락 대기 없음                                    | 되돌리는 경로·이력 정리가 복잡하고, 동시에 저장된 두 건 중 어느 쪽을 되돌릴지 정해야 한다                                                                                            |

## 5. 좌석 축소

최대 인원을 줄이면 **큰 번호 좌석부터 쓰지 않게 된다**(규칙 #7). 좌석 행은 지우지 않는다(`number > max_personnel`이면 쓰지 않는 좌석).

- 없어질 좌석에 **아직 끝나지 않은** 유효 신청이 있으면 409 `SEATS_IN_USE`로 막는다. 지난 예약·취소만 있으면 줄일 수 있다.
- 축소도 자습실 락을 잡으므로, 줄이는 순간 그 좌석에 들어오는 신청과 엇갈리지 않는다. 신청이 먼저면 축소가 `SEATS_IN_USE`로, 축소가 먼저면 신청이 `SEAT_NOT_FOUND`로 거절된다.
- 다시 늘리면 같은 번호의 좌석 행을 그대로 쓴다. 지난 신청·이력이 같은 좌석을 계속 가리킨다.

## 6. 검증: 락 유무 비교

API e2e(`apps/api/test/seats.e2e-spec.ts`의 "동시성")로 고정했다. 신청의 자습실 락(`visits.service.ts`의 `lockStudyRoom`)을 주석 처리하고 같은 테스트를 돌려 비교했다 (#48, 문서 작성 시 다시 확인).

| 테스트                                                        | 락 있음                       | 락 없음                                |
| ------------------------------------------------------------- | ----------------------------- | -------------------------------------- |
| 같은 좌석에 10명이 동시에 같은 시간을 신청                    | 1명 성공, 9명 `SEAT_TAKEN` ✅ | **10명 모두 성공** (같은 좌석 10건) ❌ |
| 좌석을 고르지 않고(자동 배정) 3석 자습실에 10명이 동시에 신청 | 3명 성공, 좌석 1·2·3번 ✅     | **10명 모두 성공** ❌                  |
| 서로 다른 좌석 5개에 5명이 동시에 신청                        | 5명 모두 성공 ✅              | 5명 모두 성공                          |

락이 없으면 모든 요청이 "아직 아무도 없다"를 본 뒤 저장해, 한 좌석·한 시간에 10건이 예약된다. 서로 다른 좌석은 원래 충돌하지 않으므로 락이 있어도 모두 성공한다(락은 차례만 정한다).

### 누가 이기는가

자습실 락을 **먼저 잡은 요청**이 이긴다(선착순). 누르는 순서가 아니라 서버에 도착해 락을 잡은 순서다. 공정성(추첨·대기열)은 동시성 제어와 별개의 정책이며, 좌석 단위에서는 대기열을 두지 않기로 했다(규칙 #14, 다른 좌석·시간을 바로 고를 수 있으므로). → 좌석 전환 전의 공정성 논의: [study-room-capacity-concurrency.md 5절](./study-room-capacity-concurrency.md#5-공정성-누가-이기는가)

## 7. 화면(웹)의 역할

규칙을 보장하는 곳은 서버다. 화면은 헛걸음을 줄이고, 진 학생이 바로 다른 좌석을 고를 수 있게 한다.

| 위치 | 처리                                                                                                                                   |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 서버 | 같은 좌석이 겹치면 409 `SEAT_TAKEN`. 화면을 거치지 않은 직접 호출과 동시 요청도 막는다                                                 |
| 화면 | 고른 시간 내내 비어 있는 좌석만 고를 수 있게 한다(`GET /study-rooms/:id/seats`). 시간을 바꿔 고른 좌석이 차면 선택을 풀고 알린다       |
| 화면 | 보는 동안 30초마다 좌석을 다시 받아, 고른 좌석을 다른 학생이 가져가면 "방금 다른 학생이 n번 좌석을 예약했어요"로 알리고 선택을 푼다    |
| 화면 | 신청 순간 졌으면(`SEAT_TAKEN`) 좌석을 다시 받고 선택을 푼 뒤 토스트와 라이브 영역으로 알린다. 빈 좌석이 0석이면 다른 자습실을 안내한다 |

## 8. 재현 방법

자동 테스트 (`pnpm db:up` 필요):

```bash
pnpm --filter @hiconsy/api test:e2e     # seats.e2e-spec.ts "동시성", visits.e2e-spec.ts "동시성"
pnpm --filter @hiconsy/web test:e2e     # 좌석 선점, 30초 자동 갱신 등
```

직접 호출로 확인하기 (개발 서버 실행 중, **개발 DB에 데이터가 생긴다**):

```bash
API=http://localhost:3000/api
id() { sed -E 's/.*"data":\{"id":([0-9]+).*/\1/'; echo; }
T='"startAt":"2030-01-10T19:00:00+09:00","endAt":"2030-01-10T21:00:00+09:00"'
R=$(curl -s -X POST $API/study-rooms -H 'Content-Type: application/json' \
  -d '{"name":"좌석 동시성","maxPersonnel":5,"startDate":"2030-01-10T09:00:00+09:00","endDate":"2030-01-10T22:00:00+09:00"}' | id)
SEAT=$(curl -s "$API/study-rooms/$R/seats?startAt=2030-01-10T19:00:00%2B09:00&endAt=2030-01-10T21:00:00%2B09:00" \
  | sed -E 's/.*"data":\[\{"id":([0-9]+).*/\1/')   # 1번 좌석 id
STUDENTS=$(for n in $(seq 1 10); do
  curl -s -X POST $API/students -H 'Content-Type: application/json' \
    -d "{\"name\":\"학생 $n\",\"phone\":\"010-8$(printf %03d $((R % 1000)))-$(printf %04d $n)\"}" | id
done)

# 10명이 같은 좌석·같은 시간으로 동시에 신청 → 201 하나, 409 SEAT_TAKEN 아홉
for s in $STUDENTS; do
  curl -s -o /dev/null -w "학생 $s → %{http_code}\n" -X POST $API/students/$s/visits \
    -H 'Content-Type: application/json' -d "{\"studyRoomId\":$R,\"seatId\":$SEAT,$T}" &
done; wait
```

웹 E2E용 DB에 붙인 API로 실행한 결과: `201` 1건, `409` 9건.

## 9. 남은 과제

- **좌석 단편화**: 좌석 방식은 "한 자리에 계속 앉는다"는 규칙이라 시간대별 인원(동시 인원 ≤ 최대 인원)보다 엄격하다. 1번 좌석 18~20시, 2번 좌석 20~22시가 예약돼 있으면 19~21시는 매 순간 한 자리가 비어 있지만 고를 수 있는 좌석이 없다. 화면은 다른 시간·다른 자습실을 안내한다. 좌석을 옮겨 앉는 예약(구간을 나눠 다른 좌석)은 범위 밖으로 두었다.
- **자습실 락의 범위**: 한 자습실의 다른 좌석 신청도 차례로 처리된다. 자습실당 30석 이하라 지금은 문제가 없지만, 좌석이 아주 많아지면 좌석 행 락으로 나누는 것을 다시 검토한다(4절).
