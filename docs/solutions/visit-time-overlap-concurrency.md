# 같은 학생의 방문 시간 겹침과 동시 요청 처리

> 관련: 이슈 #31, PR #32 · 규칙 [requirements.md 9절 #13](../requirements.md#결정한-규칙)

## 1. 문제

같은 학생이 **서로 다른 자습실**에 같은 시간대로 신청할 수 있었다. 기존 중복 검사(`ALREADY_APPLIED`)는 `UNIQUE(student_id, study_room_id)` 기준이라 한 자습실 안의 중복만 막는다.

- 한 학생이 같은 시간에 두 곳에 있을 수 없으니 실제로는 불가능한 신청이다.
- 정원이 자습실 단위라 겹친 신청은 다른 학생의 자리를 차지한다.

## 2. 규칙

같은 학생의 **유효 신청(APPLIED)끼리 방문 구간이 겹치면 안 된다** → 409 `VISIT_TIME_OVERLAP`

| 항목      | 결정                                                                                                   |
| --------- | ------------------------------------------------------------------------------------------------------ |
| 겹침 정의 | 반열린 구간 `[start, end)`. `기존.start < 새.end AND 새.start < 기존.end`                              |
| 허용      | 맞닿는 구간 (19~21시 다음 21~22시), 다른 학생과의 겹침, 취소한 신청과의 겹침                           |
| 적용 시점 | 신청 · 재신청 · 시간 수정 (수정 시 자기 자신은 비교에서 제외)                                          |
| 검사 순서 | 입력·운영 기간(400) → `ALREADY_APPLIED` → `VISIT_TIME_OVERLAP` → `CAPACITY_FULL`                       |
| 제외      | 삭제된 자습실의 신청은 삭제 시 자동 취소되므로 따로 처리하지 않는다. 취소는 겹침을 만들 수 없어 검사 X |

## 3. 왜 검사만으로는 안 되는가: 경쟁 상태

겹침 검사는 "DB에서 내 다른 신청 조회 → 없으면 저장"이다. 같은 학생의 요청 두 개가 동시에 오면 둘 다 상대의 저장을 보기 전에 조회해 **둘 다 통과**할 수 있다.

정원은 자습실 행 락(`FOR UPDATE`)으로 이미 직렬화하고 있지만, 겹침은 **자습실이 서로 다른** 요청끼리의 문제라 자습실 락이 서로 달라 막지 못한다. 그래서 **학생 행**을 잠가 같은 학생의 신청끼리 직렬화한다.

```
신청·시간 수정 트랜잭션
1. 학생 행 락 (FOR NO KEY UPDATE)   ← 같은 학생의 요청은 여기서 한 줄로 선다
2. 자습실 행 락 (FOR UPDATE)        ← 정원 보장 (기존)
3. 규칙 검사 (겹침 · 정원 …)        ← 락 이후에 조회하므로 항상 최신 커밋을 본다
4. visits 변경 + visit_histories 기록 → 커밋 (락 해제)
```

락 순서는 기존과 같이 항상 **학생 → 자습실**이라 순서 역전으로 인한 교착 상태는 없다.

## 4. 락 모드 선택: `FOR NO KEY UPDATE`

| 작업                       | 학생 행             | 자습실 행    |
| -------------------------- | ------------------- | ------------ |
| 방문 신청·재신청·시간 수정 | `FOR NO KEY UPDATE` | `FOR UPDATE` |
| 방문 취소                  | `FOR SHARE`         | `FOR UPDATE` |
| 자습실 수정·삭제           | -                   | `FOR UPDATE` |
| 학생 삭제                  | `FOR UPDATE`        | -            |

후보별 결과:

| 학생 락 (신청·수정)        | 같은 학생끼리 직렬화 | 자습실 삭제와 교착 상태 | 결과                |
| -------------------------- | -------------------- | ----------------------- | ------------------- |
| `FOR SHARE` (기존)         | ❌ 공유 락끼리 통과  | 없음                    | 겹친 신청이 저장됨  |
| `FOR UPDATE`               | ✅                   | **발생**                | `deadlock detected` |
| **`FOR NO KEY UPDATE`** ✅ | ✅                   | 없음                    | 채택                |

### `FOR UPDATE`에서 교착 상태가 나는 이유

자습실 삭제는 자습실 락을 잡은 채 유효 신청을 자동 취소하고 `visit_histories`에 행을 넣는다. 이 INSERT의 **FK 검사가 학생 행에 `FOR KEY SHARE`**를 건다.

```
시간 수정 (학생 S의 자습실 R 신청)          자습실 R 삭제
───────────────────────────────          ──────────────────────────────
학생 S  FOR UPDATE   ✅
                                         자습실 R  FOR UPDATE  ✅
자습실 R FOR UPDATE  ⏳ (삭제를 기다림)
                                         이력 INSERT → FK 검사
                                         학생 S  FOR KEY SHARE ⏳ (수정을 기다림)
                         ↻ 서로를 기다림 → PostgreSQL이 한쪽을 중단 (40P01)
```

PostgreSQL 행 락 충돌표에서 `FOR UPDATE`는 `FOR KEY SHARE`와 충돌하지만, **`FOR NO KEY UPDATE`는 충돌하지 않는다.** 그래서 삭제 쪽 FK 검사는 기다리지 않고 진행되고, 같은 학생의 신청·수정끼리는(`FOR NO KEY UPDATE`끼리 충돌) 여전히 직렬화된다.

|                     | FOR KEY SHARE | FOR SHARE | FOR NO KEY UPDATE | FOR UPDATE |
| ------------------- | :-----------: | :-------: | :---------------: | :--------: |
| `FOR KEY SHARE`     |               |           |                   |     X      |
| `FOR SHARE`         |               |           |         X         |     X      |
| `FOR NO KEY UPDATE` |               |     X     |         X         |     X      |
| `FOR UPDATE`        |       X       |     X     |         X         |     X      |

(X = 충돌. [PostgreSQL 문서: Row-Level Locks](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS))

## 5. 검토한 다른 방법: DB 배제 제약

```sql
CREATE EXTENSION btree_gist;
ALTER TABLE visits ADD CONSTRAINT visits_no_overlap
  EXCLUDE USING gist (student_id WITH =, tstzrange(start_at, end_at) WITH &&)
  WHERE (status = 'APPLIED');
```

DB가 직접 보장해 락 설계가 필요 없다는 장점이 있지만 채택하지 않았다.

- Prisma 스키마로 표현할 수 없어 마이그레이션 SQL을 손으로 관리해야 하고, `migrate dev`가 스키마와 DB가 어긋났다고 판단할 위험이 있다.
- `btree_gist` 확장이 필요하다.
- 정원 보장과 같은 방식(트랜잭션 + 행 락)으로 맞추는 편이 코드를 읽는 사람에게 일관적이다.

## 6. 검증: 동시 요청 비교

API 서버 두 대를 테스트 DB에 띄워 같은 시나리오를 실행했다. 한 대는 신청·수정의 학생 락만 이전 방식(`FOR SHARE`)으로 되돌린 빌드이고, 겹침 검사 코드는 두 서버에 똑같이 있다.

### ① 한 학생이 자습실 5곳에 같은 시간(19~21시)으로 동시에 신청

|                       | 응답                                  | DB에 남은 유효 신청         |
| --------------------- | ------------------------------------- | --------------------------- |
| 이전 락 (`FOR SHARE`) | 201 × 5                               | A~E 5곳 모두 19:00~21:00 ❌ |
| 현재 코드             | 201 × 1, 409 `VISIT_TIME_OVERLAP` × 4 | C 자습실 1건 ✅             |

### ② 겹치지 않던 A(10~12시)·B(19~21시) 신청을 동시에 둘 다 15~17시로 수정

|                       | 응답                          | DB 상태                                    |
| --------------------- | ----------------------------- | ------------------------------------------ |
| 이전 락 (`FOR SHARE`) | 200, 200                      | A·B 모두 15:00~17:00 ❌                    |
| 현재 코드             | 200, 409 `VISIT_TIME_OVERLAP` | A 15:00~17:00, B는 원래대로 19:00~21:00 ✅ |

**동시성 증명이 되는 이유**: 이전 락 서버에도 겹침 검사가 있으므로, 요청이 순서대로 처리됐다면 두 번째부터 409가 났어야 한다. 모두 통과했다는 것은 요청들이 서로의 저장을 보기 전에 동시에 검사를 통과했다는 뜻이다.

### 누가 이기는가

②에서 A가 이긴 데에는 업무상 이유가 없다. **학생 행 락을 먼저 잡은 요청이 이긴다.**

| 시점 | A 수정 요청                    | B 수정 요청                       |
| ---- | ------------------------------ | --------------------------------- |
| t1   | 학생 락 획득 ✅                | 학생 락 요청 → 대기               |
| t2   | 겹침 검사: B는 19~21시 → 통과  |                                   |
| t3   | 15~17시로 저장, 커밋 → 락 해제 |                                   |
| t4   |                                | 학생 락 획득                      |
| t5   |                                | 겹침 검사: A가 이미 15~17시 → 409 |

동시에 보낸 요청이 DB 락에 닿는 순서는 프로세스 실행 시점, 커넥션 풀, 네트워크 타이밍에 따라 매번 달라진다. ①에서 처음 보낸 #1이 아니라 #3이 이긴 것도 같은 이유다.

- **보장함**: 같은 학생의 유효 신청은 겹치지 않고, 동시에 와도 정확히 하나만 성공한다. 진 쪽은 원래 상태를 유지한다.
- **보장하지 않음**: 어느 쪽이 이기는지 (DB 락 선착순).

같은 학생이 동시에 요청하는 경우는 사실상 중복 클릭이나 여러 탭뿐이라 선착순으로 충분하다. 진 쪽은 화면에서 409 안내를 받고 내 신청이 다시 불러와진다. 테스트도 "A가 성공한다"가 아니라 "200 하나, 409 하나"를 검사한다.

## 7. 화면(웹)의 역할

규칙을 보장하는 곳은 서버다. 화면은 헛걸음을 줄이는 안내 역할만 한다.

| 위치 | 처리                                                                                                                        |
| ---- | --------------------------------------------------------------------------------------------------------------------------- |
| 서버 | 겹치면 409 `VISIT_TIME_OVERLAP`. 화면을 거치지 않은 직접 호출과 동시 요청도 막는다                                          |
| 화면 | 내 신청 목록 기준으로 겹치는 시각을 "다른 신청" 표시와 함께 비활성화, 고른 시간이 겹치면 이유를 보여주고 제출 버튼 비활성화 |
| 화면 | 목록이 낡아(다른 탭에서 신청 등) 서버가 409를 주면 안내 후 내 신청을 다시 받아 선택지를 맞춘다                              |

## 8. 재현 방법

자동 테스트 (`pnpm db:up` 필요):

```bash
pnpm --filter @hiconsy/api test:e2e     # "다른 자습실과 방문 시간 겹침", "동시성" 그룹
pnpm --filter @hiconsy/web test:e2e     # "내 다른 신청과 겹치는 시간은 고를 수 없다" 등
```

| 테스트 (`apps/api/test/visits.e2e-spec.ts`)                                 | 락을 바꾸면                              |
| --------------------------------------------------------------------------- | ---------------------------------------- |
| 같은 학생이 여러 자습실에 같은 시간으로 동시에 신청해도 1건만 성공한다      | `FOR SHARE`: 실패 (여러 건 성공)         |
| 같은 학생이 두 신청을 서로 겹치게 동시에 수정해도 1건만 성공한다            | `FOR SHARE`: 실패 (둘 다 성공)           |
| 시간 수정과 그 신청의 자습실 삭제가 동시에 일어나도 교착 상태 없이 처리된다 | `FOR UPDATE`: 실패 (`deadlock detected`) |

직접 호출로 확인하기 (개발 서버 실행 중, **개발 DB에 데이터가 생긴다**):

```bash
API=http://localhost:3000/api
S=$(curl -s -X POST $API/students -H 'Content-Type: application/json' \
  -d '{"name":"동시성 테스트","phone":"010-9999-0001"}' | sed -E 's/.*"data":\{"id":([0-9]+).*/\1/')
ROOMS=$(for n in 1 2 3 4 5; do
  curl -s -X POST $API/study-rooms -H 'Content-Type: application/json' \
    -d "{\"name\":\"동시성 $n\",\"maxPersonnel\":10,\"startDate\":\"2030-01-10T09:00:00+09:00\",\"endDate\":\"2030-01-10T22:00:00+09:00\"}" \
    | sed -E 's/.*"data":\{"id":([0-9]+).*/\1/'
done)

# 5곳에 같은 시간으로 동시에 신청 → 201 하나, 409 VISIT_TIME_OVERLAP 넷
for r in $ROOMS; do
  curl -s -o /dev/null -w "room $r → %{http_code}\n" -X POST $API/students/$S/visits \
    -H 'Content-Type: application/json' \
    -d "{\"studyRoomId\":$r,\"startAt\":\"2030-01-10T19:00:00+09:00\",\"endAt\":\"2030-01-10T21:00:00+09:00\"}" &
done; wait
```

## 9. 남은 과제

- **학생 삭제 ↔ 자습실 삭제 동시 실행**: 같은 신청을 둘 다 자동 취소하려 하면 비슷한 교착 상태가 날 수 있어 보인다. 둘 다 각자의 행을 `FOR UPDATE`로 잡은 채 이력 INSERT의 FK 검사로 상대 행에 `FOR KEY SHARE`를 걸기 때문이다. 이번 변경과 무관한 기존 경로라 아직 재현하지 않았고, 별도 이슈로 다룬다.
