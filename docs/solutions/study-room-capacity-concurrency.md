# 정원 마감 직전의 동시 신청 처리

> 관련: 이슈 #33 · 규칙 [requirements.md 2절 정원, 9절 #2·#5](../requirements.md) · 같은 형식의 문서: [visit-time-overlap-concurrency.md](./visit-time-overlap-concurrency.md)

## 1. 문제

정원이 1자리, 또는 2~3자리처럼 **조금 남은 자습실에 남은 자리보다 많은 학생이 동시에 신청**하면, 정원을 넘겨 등록될 수 있다.

신청 로직은 **검사 후 저장(check-then-act)** 구조다.

```
1. 현재 유효 신청 수를 센다          SELECT count(*) FROM visits WHERE study_room_id = ? AND status = 'APPLIED'
2. maxPersonnel보다 작으면           (4 < 5 → 통과)
3. 신청을 저장한다                   INSERT INTO visits ...
```

두 요청이 1번을 동시에 실행하면 둘 다 "4명"을 보고 통과한 뒤 각자 저장한다. 결과는 6/5명이다. 검사와 저장 사이에 다른 트랜잭션이 끼어들 수 있다는 점이 문제다.

> 트랜잭션만으로는 막히지 않는다. PostgreSQL 기본 격리 수준(READ COMMITTED)에서는 두 트랜잭션이 각자 커밋 전 상태를 보고 count가 같게 나오고, INSERT끼리는 서로 충돌하지 않는다.

## 2. 해결: 자습실 행 `FOR UPDATE`로 직렬화

신청 트랜잭션은 **인원을 세기 전에 자습실 행을 배타 락으로 잠근다** (`lockStudyRoom()`, `apps/api/src/study-rooms/study-room-lock.ts`).

```
신청 트랜잭션 (VisitsService.apply)
1. 학생 행 락 (FOR NO KEY UPDATE)              ← 학생 삭제·같은 학생 시간 겹침용 (#31)
2. SELECT id FROM study_rooms
     WHERE id = ? AND deleted_at IS NULL
     FOR UPDATE                                 ← 같은 자습실 요청은 여기서 한 줄로 선다
3. 운영 기간 · 중복 · 시간 겹침 검사
4. 유효 신청 수 count → maxPersonnel 이상이면 409 CAPACITY_FULL
5. visits 저장 + visit_histories(APPLY) 기록 → 커밋 (락 해제)
```

- 뒤에 온 트랜잭션은 2번에서 기다리다가, 앞 트랜잭션이 커밋한 뒤에 락을 잡는다. 그러고 나서 4번에서 다시 세므로 **앞에서 커밋된 인원을 반드시 본다** (READ COMMITTED는 문장마다 새 스냅샷을 쓴다).
- **남은 자리가 여러 개여도 같다.** 락은 남은 자리 수와 상관없이 자습실 단위로 한 번에 하나씩 들여보내므로, 먼저 락을 잡은 순서대로 자리가 찰 때까지만 성공하고 그 뒤는 모두 `CAPACITY_FULL`이다.

  ```
  정원 5명, 현재 2명 (남은 자리 3) — 10명 동시 신청
  요청1 락 획득 → 인원 2 < 5 → 저장(3명) → 커밋, 락 해제
  요청2 락 획득 → 인원 3 < 5 → 저장(4명) → 커밋
  요청3 락 획득 → 인원 4 < 5 → 저장(5명) → 커밋
  요청4 락 획득 → 인원 5 ≥ 5 → 409 CAPACITY_FULL (롤백)
  요청5~10 마찬가지로 409
  ```

- 같은 락을 쓰는 작업: 신청 · 재신청 · 시간 수정 · 취소 · 자습실 수정(정원 축소 검사) · 자습실 삭제. 그래서 "정원 축소 vs 신청", "취소 vs 신청"도 엇갈리지 않는다.
- **락 범위는 자습실 1행**이다. 다른 자습실 신청은 기다리지 않고, 같은 자습실 요청끼리만 줄을 선다.
- 현재 인원은 카운터 컬럼 없이 `visits(study_room_id, status)` 인덱스로 매번 센다. 상태와 카운터가 어긋날 일이 없다.

## 3. 검증

### 3-1. e2e 테스트 (`apps/api/test/visits.e2e-spec.ts` › 동시성)

| 테스트                                                                                     | 현재 코드 | `FOR UPDATE` 제거 시           |
| ------------------------------------------------------------------------------------------ | --------- | ------------------------------ |
| 정원 3명 자습실에 10명이 동시에 신청해도 3명만 성공한다 (빈 자습실, 남은 자리 3)           | 통과      | **실패**: 10명 전원 성공       |
| 정원 마지막 1자리 › 20명이 동시에 신청해도 1명만 성공                                      | 통과      | **실패**: 9명 성공             |
| 정원 마지막 1자리 › 재신청(취소했던 학생)과 신규 신청이 동시에 와도 1건만 성공             | 통과      | **실패**: 3명 모두 성공        |
| 정원 축소와 신청이 동시에 일어나도 정원을 넘지 않는다                                      | 통과      | **실패**: 축소·신청 둘 다 성공 |
| 정원 마지막 1자리 › 정원이 찬 자습실에서 취소와 신규 신청이 동시에 와도 정원을 넘지 않는다 | 통과      | 통과 (아래 참고)               |

- "락 제거 시" 결과는 소스를 고치지 않고, 테스트 실행 때만 `study-room-lock` 모듈을 `FOR UPDATE` 없는 버전으로 바꿔 끼워 얻었다(vitest `resolve.alias`).
- **취소 vs 신청** 테스트는 락이 없어도 통과한다. 취소는 인원을 줄이기만 하므로, 신청이 취소 전 인원을 봐도 "거절"이 될 뿐 정원을 넘지는 않는다. 이 테스트는 정원 초과가 아니라 **두 순서 모두 결과가 일관적인지**(취소가 먼저면 B 성공 · 1명, 신청이 먼저면 B 거절 · 0명)를 지키는 회귀 테스트다. 30회 실행해 보니 신청이 먼저 락을 잡은 경우가 19회, 취소가 먼저 커밋된 경우가 11회로, 두 경로가 모두 실제로 실행됐다.

### 3-2. 동시 요청 시연 (락 있음 vs 없음)

정원 5명 자습실에 미리 신청을 채워 **남은 자리를 1·2·3개**로 만든 뒤, 학생 N명이 동시에 신청했다. API 빌드 두 개를 테스트 DB에 띄웠고, 한쪽만 `lockStudyRoom()`의 `FOR UPDATE`를 지웠다. 나머지 코드는 같다.

**남은 자리 1 (정원 5명 중 4명 신청)**

| 동시 신청 | 락 없음: 성공 / 최종 인원 | 현재 코드: 성공 / 최종 인원 | 현재 코드: 가장 느린 응답 |
| --------- | ------------------------- | --------------------------- | ------------------------- |
| 2명       | 1명 / 5 (우연히 정상)     | 1명 / **5** ✅              | 0.03s                     |
| 10명      | 2명 / **6** ❌            | 1명 / **5** ✅              | 0.18s                     |
| 50명      | 3명 / **7** ❌            | 1명 / **5** ✅              | 0.08s                     |
| 150명     | 4명 / **8** ❌            | 1명 / **5** ✅              | 0.20s                     |

**남은 자리 2 (정원 5명 중 3명 신청)**

| 동시 신청 | 락 없음: 성공 / 최종 인원 | 현재 코드: 성공 / 최종 인원 | 현재 코드: 가장 느린 응답 |
| --------- | ------------------------- | --------------------------- | ------------------------- |
| 10명      | 9명 / **12** ❌           | 2명 / **5** ✅              | 0.05s                     |
| 50명      | 4명 / **7** ❌            | 2명 / **5** ✅              | 0.07s                     |
| 150명     | 3명 / **6** ❌            | 2명 / **5** ✅              | 0.23s                     |

**남은 자리 3 (정원 5명 중 2명 신청)**

| 동시 신청 | 락 없음: 성공 / 최종 인원 | 현재 코드: 성공 / 최종 인원 | 현재 코드: 가장 느린 응답 |
| --------- | ------------------------- | --------------------------- | ------------------------- |
| 10명      | 8명 / **10** ❌           | 3명 / **5** ✅              | 0.02s                     |
| 50명      | 4명 / **6** ❌            | 3명 / **5** ✅              | 0.07s                     |
| 150명     | 6명 / **8** ❌            | 3명 / **5** ✅              | 0.19s                     |

- 현재 코드는 남은 자리가 몇 개든 **정확히 남은 자리 수만큼만 성공**했고(1·2·3명), 최종 인원은 항상 5/5였다. 150명이 동시에 신청해도 가장 느린 응답은 0.2초 안팎이고, 500 에러나 트랜잭션 타임아웃은 없었다.
- 락이 없으면 초과 인원이 **들쭉날쭉하다**(남은 자리 2에서 10명 → 12/5, 150명 → 6/5). 경쟁 상태는 요청들이 얼마나 정확히 같은 순간에 count를 실행하느냐에 달린 **확률적** 현상이라서, 락이 없어도 남은 자리 1에 2명일 때는 우연히 맞았다. "몇 번 해 봤는데 괜찮다"로는 검증이 안 되는 이유이고, 테스트가 많은 동시 요청과 반복 실행을 쓰는 이유다.

## 4. 다른 방법과 비교

| 방법                                            | 방식                                                                                                        | 장점                                                     | 단점 / 채택하지 않은 이유                                                                                  |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **비관적 락 `FOR UPDATE`** ✅                   | 자습실 행을 잠그고 세고 저장                                                                                | 단순, 정원 외 규칙(기간·중복·겹침)도 같은 락 안에서 검사 | 같은 자습실 요청은 순서대로 처리 (이 규모에선 문제없음)                                                    |
| 조건부 UPDATE + 카운터                          | `UPDATE study_rooms SET current = current + 1 WHERE id = ? AND current < max_personnel`, 영향 행 0이면 마감 | 한 문장으로 원자적, 락 대기 짧음                         | 카운터 컬럼을 신청·취소·재신청·자동 취소마다 맞춰야 해 상태와 어긋날 위험. 정원 외 검사는 어차피 따로 필요 |
| 낙관적 락 (version + 재시도)                    | 읽을 때 version을 기억, 저장 시 `WHERE version = ?`로 충돌 감지 후 재시도                                   | 충돌이 드물면 락 대기가 없음                             | 마지막 자리처럼 **충돌이 몰리는** 상황에선 재시도 폭주. 재시도 로직 필요                                   |
| `SERIALIZABLE` 격리 + 재시도                    | DB가 직렬화 이상을 감지해 한쪽을 실패(40001)시킴                                                            | 코드에 락이 드러나지 않음                                | 실패한 트랜잭션을 앱이 재시도해야 함. 실패 원인을 도메인 에러로 바꾸기 어려움                              |
| Advisory lock (`pg_advisory_xact_lock(roomId)`) | 행이 아닌 임의 키로 잠금                                                                                    | 행 없이도 잠글 수 있음                                   | 행 락으로 충분한데 키 규칙을 따로 관리해야 함. 자습실 행 락과 효과가 같음                                  |
| 분산 락 · 큐 (Redis, 메시지 큐)                 | 앱 바깥에서 줄 세우기                                                                                       | 대규모 트래픽, 여러 DB에 걸친 작업                       | 인프라 추가. 단일 PostgreSQL로 끝나는 이 규모에는 과함                                                     |
| DB 제약                                         | -                                                                                                           | -                                                        | "유효 신청 수 ≤ max_personnel"처럼 **여러 행에 걸친 개수 조건**은 CHECK·UNIQUE 제약으로 표현할 수 없음     |

결론: 신청 한 건에서 정원 말고도 운영 기간, 중복, 시간 겹침을 함께 검사해야 하므로, **검사 전체를 하나의 락 안에 넣는 비관적 락**이 가장 단순하고 확실하다. 학원 자습실 규모(자습실당 수십 명)에서는 줄 서기 비용이 측정상 무시할 만하다.

## 5. 공정성: 누가 이기는가

### 순서가 정해지는 곳

```
학생 기기 → 네트워크 → API 서버 → DB 커넥션 대기 → 자습실 행 락 대기 → 정원 검사·저장
                                    (pg 풀, 기본 10개)   (먼저 잡은 쪽이 먼저)
```

- 결과를 정하는 건 **자습실 행 락을 먼저 잡은 요청**이다. 먼저 잡은 요청이 커밋해야 다음 요청이 락을 잡는다.
- 락에 닿는 순서는 네트워크 지연, 서버가 요청을 처리하는 타이밍, 커넥션을 받는 순서에 따라 정해진다. 커넥션 대기열과 PostgreSQL 행 락 대기열은 대체로 도착 순서(FIFO)에 가깝지만, 엄밀한 순서 보장은 아니다.
- 그래서 결과는 **서버 도착 기준 선착순**이다. 네트워크가 빠른 쪽이 유리한 건 맞지만, 차이는 보통 수 ms에서 수십 ms로 사람이 버튼을 누르는 시간 차보다 훨씬 작다. 같은 순간에 보낸 요청끼리는 사실상 무작위다. #31 시연에서도 처음 보낸 #1이 아니라 #3이 이겼다.

### 동시성 제어는 정확성, 공정성은 정책

동시성 제어가 책임지는 건 **정확성**이다. 정원을 넘지 않고, 정확히 남은 자리 수만큼만 성공하며, 진 쪽은 아무 흔적(신청·이력)도 남기지 않는다. **누가 이기는가**(공정성)는 동시성 기법이 아니라 신청 정책이 정한다. 위 4절의 방법들은 모두 "어딘가에서 줄을 세우고 먼저 온 쪽이 이긴다"는 같은 원리이고, 줄을 세우는 위치만 다르다.

### 선착순을 택한 이유

- 기존 운영이 단톡방 **선착순**이었다. 사용자가 기대하는 규칙을 그대로 옮겼다.
- 자습실당 수십 명 규모라, 같은 ms에 몰리는 경쟁은 드물고 생겨도 차이를 체감할 수 없다.
- 진 쪽은 즉시 409 `CAPACITY_FULL`을 받는다. 화면은 목록을 다시 받아, 같은 시간에 자리가 남은 자습실이 있으면 "{자습실} 정원이 방금 찼어요" 안내와 [이 시간으로 신청]을 보여주고(#35, 화면 명세 S-23), 없으면 "방금 정원이 다 찼어요. 다른 자습실을 골라 주세요"로 알린다.

### 네트워크 속도와 무관해야 해질 때의 확장 방법

락을 바꿔서는 해결되지 않고, 신청 방식(정책) 자체를 바꿔야 한다.

| 방법               | 방식                                                                                    | 적합한 경우                                | 이 프로젝트에 넣는다면                                                                |
| ------------------ | --------------------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------- |
| 추첨               | 신청 기간 동안 모두 받고, 마감 후 무작위로 정원만큼 확정                                | 인기 자습실이 정해진 시각에 열려 몰릴 때   | 자습실에 "신청 마감 일시"와 `PENDING → APPLIED/REJECTED` 상태, 마감 시 추첨 작업 추가 |
| 대기열 (자리 제안) | 정원이 차면 대기 순번으로 받고, 자리가 나면 다음 순번에게 **자리를 제안**해 본인이 확정 | 선착순은 유지하되 진 쪽의 헛걸음을 줄일 때 | 대기·제안 상태와 만료 시각 추가. 확정은 기존 신청 흐름 재사용 → #36                   |
| 가상 대기실        | 접속 순서대로 번호표를 주고 순서대로 신청 화면에 입장                                   | 수만 명이 동시에 몰리는 예매               | 별도 인프라(Redis 등) 필요. 이 규모에는 과함                                          |

- 클라이언트가 보낸 "누른 시각"을 기준으로 줄 세우는 방식은 시계를 조작할 수 있어서 쓰지 않는다. 순서의 기준은 항상 서버가 정한다.
- **대기열은 자동 확정이 아니라 자리 제안 방식이어야 한다.** 취소 시 다음 대기자를 바로 `APPLIED`로 올리는 자동 확정은 다음 이유로 쓰지 않는다.
  - **시간 겹침 규칙(#13)과 충돌**: 대기 중에 다른 자습실의 같은 시간을 신청했다면 자동 확정 시 겹치는 신청이 생긴다. 대기가 시간을 차지한다고 보면, 언제 풀릴지 모르는 대기 때문에 다른 선택지가 막힌다.
  - **락 순서 역전**: 취소 트랜잭션은 이미 자습실 락을 잡고 있는데, 대기자의 겹침을 검사하려면 그 학생의 락이 필요하다. 기존 순서(학생 → 자습실)와 반대가 되어 교착 상태 위험이 생긴다 ([visit-time-overlap-concurrency.md](./visit-time-overlap-concurrency.md) 4절).
  - **학생이 알 수 없음**: 로그인·알림이 없어 확정된 줄 모르면 오지 않고, 자리는 빈 채로 남는다.
- 자리 제안 방식에서는 취소 트랜잭션이 **제안 행만 만들고**, 학생이 [확정]을 누르면 기존 신청 흐름(학생 락 → 자습실 락 → 정원·겹침 검사)이 그대로 실행된다. 대기는 시간을 차지하지 않으므로 대기 중에도 다른 자습실을 자유롭게 신청할 수 있다.
- 현재는 대기열 없이 **거절 후 다른 자습실로 안내**한다. 거절되면 같은 시간에 자리가 남은 자습실을 바로 보여주고, 고르면 그 시간이 채워진 신청 다이얼로그로 이어진다(#35). 신청은 기존 흐름이라 정원·겹침 규칙과 락은 그대로다. 대기열(자리 제안)은 #36에서 다룬다.

## 6. 한계

- **초고부하**: 한 자습실에 요청이 수백~수천 건씩 몰리면, 락보다 **DB 커넥션 풀**(pg 기본 10개)과 Prisma 대화형 트랜잭션의 대기 시간(기본 `maxWait` 2초, `timeout` 5초)이 먼저 한계가 된다. 대기 초과 시 500이 날 수 있다. 150명 동시 신청까지는 문제없음을 확인했고, 필요해지면 `lock_timeout`·풀 크기 조정, 대기 초과를 503/409로 바꾸기, 대기열 도입을 별도 이슈로 다룬다.
- **응답 대기**: 같은 자습실 요청은 순서대로 처리되므로, 뒤에 선 요청은 앞 트랜잭션 시간만큼 기다린다. 트랜잭션 안에서는 DB 작업만 하고 외부 호출을 하지 않는 원칙을 지켜야 한다.

## 7. 재현 방법

```bash
pnpm db:up
pnpm --filter @hiconsy/api test:e2e     # visits.e2e-spec.ts › 동시성 › 정원 마지막 1자리
```

직접 호출로 확인하기 (개발 서버 실행 중, **개발 DB에 데이터가 생긴다**):

```bash
API=http://localhost:3000/api
ID='s/.*"data":\{"id":([0-9]+).*/\1/'
ROOM=$(curl -s -X POST $API/study-rooms -H 'Content-Type: application/json' \
  -d '{"name":"마지막 자리","maxPersonnel":1,"startDate":"2030-01-10T09:00:00+09:00","endDate":"2030-01-10T22:00:00+09:00"}' | sed -E "$ID")
STUDENTS=$(for i in $(seq 1 10); do
  curl -s -X POST $API/students -H 'Content-Type: application/json' \
    -d "{\"name\":\"동시$i\",\"phone\":\"010-7777-$(printf %04d $i)\"}" | sed -E "$ID"
done)

# 1자리에 10명이 동시에 신청 → 201 하나, 409 CAPACITY_FULL 아홉
for s in $STUDENTS; do
  curl -s -o /dev/null -w "student $s → %{http_code}\n" -X POST $API/students/$s/visits \
    -H 'Content-Type: application/json' \
    -d "{\"studyRoomId\":$ROOM,\"startAt\":\"2030-01-10T19:00:00+09:00\",\"endAt\":\"2030-01-10T21:00:00+09:00\"}" &
done; wait
```
